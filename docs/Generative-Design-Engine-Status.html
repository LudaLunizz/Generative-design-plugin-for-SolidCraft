Generative Design Engine - Status

SolidCraft plugin · version 0.3.0 · 17 Nov 2026 · ~/project SolidCraft/generative-design-engine (local git)
In short: the 0.1 plugin did not work and its results were made up. It is rebuilt as a real SolidCraft component with an 11-material engineering library (SolidCraft's own material cards) and a per-body material report. It is installed in SolidCraft 0.42 and passes an end-to-end test there. Generative design and stress analysis are withdrawn until a real solver backs them.

What was wrong in 0.1

  • plugin.wasm was SolidCraft's sample test component (it makes two boxes), not this plugin's code. The Rust code was never built to WebAssembly.
  • optimize and analyze returned invented numbers: a fixed "original volume", stress = max_stress x 0.7, and the same critical point (25, 0, 0) for every part.
  • The manifest would be refused: it granted the non-existent command commands.run, asked for a 300 s deadline (max 30 s) and 512 MiB (default ceiling 128 MiB).
  • The material "library" was one default, with density in the wrong unit (2.7e-6).

Hardening

  • Hostile input refused before any edit (unknown fields, non-objects, bad numbers, empty, duplicate or oversized body names). No unwrap/expect/panic/indexing outside tests (clippy-denied).
  • Host errors pass through, so SolidCraft rolls back; cancel is checked before each edit; a same-named design material with other values is never overwritten.
  • Limits 2e9 fuel / 64 MiB / 15 s, inside the default ceilings. The component imports only craft:plugin (no WASI); build.sh refuses anything else.
  • plugin.json is generated from the library; a test fails if they drift.

Tests

  • 24 Rust tests (library validation, fake-host tests of every entry, hostile params, manifest rules).
  • tests/cli-test.sh in the installed SolidCraft 0.42: all 11 materials pass SolidCraft's card check, masses correct, reapply reuses, undo, bad input refused, the saved design reopens with its materials without the plugin. Result: PASS.

SolidCraft 0.42 findings

  • material.list and material.inspect only read but are not marked read-only, so a read entry may not call them. The report takes strengths from the library and checks the measured density.
  • 0.42's plugin.install takes only path, replace and dry_run (the docs describe a newer one with approvals).

Solver benchmark (17 Nov, v0.2.1)

New: a 2D stress solver and SIMP optimiser (src/topo2d.rs, own code from the textbook method: bilinear plane-stress cells, Jacobi-preconditioned conjugate gradients, density filter, optimality-criteria update) and a solver-benchmark entry. Checks: a solid cantilever matches beam theory within a few percent; the cantilever and MBB results show the known truss layouts; compliance drops about 5x at 50% material.

A full run (100 iterations) takes 2.4 s native at 60 x 30 and 20 s at 120 x 60, so inside SolidCraft only the smallest grid fits today. Two causes, both fixable:

  • Too many solver steps: the simple preconditioner needs about 320 steps per stress solve at 60 x 30 and about 1400 at 240 x 120, growing with the grid. A multigrid preconditioner needs a few dozen whatever the size (expected 20-50x fewer).
  • A slow inner loop: one cell's stiffness product costs about 2600 fuel (Wasm operations) where about 200 should do; the bounds-checked lookups and recomputed node numbers can go (expected about 5-10x).

Limits: fuel is a setting (Preferences › Plugins, default ceiling 1e11, the plugin asks for 1e11); the 30 s deadline is fixed. Inside SolidCraft runs 4x slower than native. Target after both fixes: 120 x 60 with 100 iterations in a few seconds.

Scripts: tests/bench-wasm.sh (in SolidCraft + native + fuel bisection), cargo run --release --example bench -- NX NY ITERATIONS [cantilever|mbb].

Speed round 1: multigrid and faster loops (17 Nov, v0.2.2)

Result: a full 120 x 60 optimisation (100 design iterations) now runs inside SolidCraft in 3.1 s; before it did not fit at all. 60 x 30 takes 0.9 s.

What changed, in order of effect:

  • Multigrid preconditioner (src/mg2d.rs): solver steps per stress solve fell from 320-1430 to about 10 at any grid size (72 302 to 909 in total at 120 x 60). Coarse grids are the exact Galerkin product, built per coarse cell; a test checks them against the slow global product.
  • Compiler optimisation for speed instead of size: about 2.5x on everything.
  • Filter and update: the volume check no longer runs the filter about 40 times per iteration (the filtered volume is a weighted sum); filter weights precomputed. 0.90 s to 0.16 s.
  • Sparse coarse-grid product (only the non-zero interpolation weights) and a SIMD stiffness product in WebAssembly.

Fuel per call inside SolidCraft at 120 x 60 (measured by bisection): stiffness product 9.1 M to 2.4 M, V-cycle 82 M to 33 M, multigrid setup 420 M to 117 M. One design iteration is now about 0.44 billion: V-cycles about 70%, setup about 27%.

Next for larger grids: SIMD and packed matrices on the coarse grids, cheaper restriction and interpolation, building the coarse-grid weights once instead of per cell, a direct diagonal. Expected another 2-3x, enough for 160 x 80 within the default fuel ceiling. Raising the ceiling in Preferences also works, as long as the run stays under 30 s.

Stress check (17 Nov, v0.3.0)

New entry stress-check (Model › Plugins): say where a flat part is held and where a force acts, and it gives the peak stress and where, the safety factor against the material's strength (pass or not), the largest displacement and a text heat map. Faces by name (F2:bore:side:0), number, or side (-x); screw holes work as supports.

Method: the body's mesh is sampled on a grid at mid-thickness (rays through the thickness), plane stress with the multigrid solver, von Mises stress per cell. Limits, all reported as warnings when they apply: flat parts of one thickness only; force through the plate ignored; linear elastic, small deflections, rigid supports, the load spread evenly; peaks at sharp inside corners depend on the grid (the 99th percentile is reported beside the peak).

Also fixed: SolidCraft's plugin dialog cannot draw list fields and switched Run off for apply-material and material-report. They now have a Body text field (empty = all bodies); a new test checks that every entry stays drawable.

Wall foot: why the stress check cannot run on it (17 Nov)

  • It is a 3D part. The foot (140 x 100 x 211 mm: wall plate, cone, 24 x 29 mm post, hinge head) is not a flat plate of one thickness; the 2D check would treat its side outline as 100 mm thick everywhere, and the worst case of 29 Oct (the 20 N poke, perpendicular to the screen) pushes through that outline, which plane stress ignores.
  • The plugin cannot read its mesh. SolidCraft hands meshes to plugins unwelded (three points per triangle): 6138 triangles = 18 414 points, over the plugin limit of 8192 ("mesh exceeds the plugin transfer budget").
  • The mesh has one open seam. Wall-Foot.stl: 3099 vertices, 6138 triangles, no edge on more than two triangles, but 88 open edges (146 mm in all) in a ring at z = -204 to -200 mm, x 179-241, y 92-163: where the cone meets the wall plate. SolidCraft therefore reports the body as not closed. Slicers usually close such a seam; check the slicer preview there.

The foot needs a 3D check, as the 29 Oct Python voxel model did (tools/foot_fem_heatmap.py). The same Rust solver can do 3D voxels; as a command-line tool it reads the STL directly and has no plugin limits.
